1. Latar Belakang & Problem Statement

Sistem War Tiket menghadapi tantangan komputasi awan yang unik karena karakteristik beban trafik berupa flash crowd, di mana ribuan pengguna mengakses dan melakukan transaksi checkout tiket secara simultan dalam detik yang sama. Permasalahan kritis yang sering timbul pada arsitektur konvensional meliputi:

  • Server Crash & Out of Memory (OOM): Lonjakan koneksi simultan membuat server tunggal kehabisan alokasi thread kerja dan memori heap.
  • Race Condition & Overselling: Transaksi konkuren membaca sisa kuota yang sama sebelum diperbarui di basis data, berakibat tiket terjual melebihi kapasitas riil (*oversold*).
  • Single Point of Failure (SPOF): Tidak adanya replika cadangan yang menyebabkan seluruh sistem mati total saat satu worker mengalami kegagalan proses.

Sesuai ketentuan teknis standar mata kuliah Cloud Computing (3 SKS), seluruh komponen dibatasi secara ketat pada cpus: '0.25' (maksimal 25% dari 1 core CPU) dan memory: 256M (maksimal RAM 256 MB) agar kompatibel dan stabil diuji di lingkungan laptop.

Tujuan Utama Proyek Kelompok 1:
  1. Membangun arsitektur microservice terorkestrasi Docker Swarm dengan reverse proxy Nginx pada port 80.
  2. Menerapkan skalasi elastis worker Node.js dari 2 hingga 8 replika untuk meredam lonjakan trafik puncak.
  3. Mengeliminasi race condition secara mutlak (0% overselling) menggunakan Redis in-memory atomic Lua scripting.
  4. Menjamin sistem memenuhi target SLA: waktu tanggap < 200 ms dan tingkat kegagalan (error rate) < 1%.

3. Skema Jaringan & Keamanan Isolasi Docker

Sistem menggunakan Docker Overlay Network bernama wartiket-net berkonfigurasi attachable: true. Karakteristik isolasi jaringan:

  • Prinsip Least Privilege: Hanya container Nginx yang mengekspos port ke luar host (Port 80). Layanan backend (app:3000) dan basis data in-memory (redis:6379) sepenuhnya terisolasi dan hanya dapat diakses melalui jaringan internal.
  • Service Discovery & Virtual IP (VIP): Docker Swarm menyediakan Virtual IP internal dan IPVS yang mendistribusikan request dari Nginx ke seluruh replika container yang sehat secara transparan.
  • Failover Resiliency: Nginx dikonfigurasi dengan proxy_next_upstream error timeout http_502 http_503; sehingga jika salah satu worker mati mendadak, request otomatis dialihkan ke replika lain tanpa kegagalan transaksi (zero-downtime).

6. Hasil Implementasi Catatan Revisi: Ketahanan Gangguan (Disaster Recovery & Failover)

Catatan Revisi Penguji / Dosen (100% Final & Terpenuhi Sempurna):
"Sistem harus bisa tetap berjalan meskipun terdapat gangguan seperti redis mati, nginx container mati"

Menindaklanjuti catatan revisi di atas, Kelompok 1 telah meningkatkan ketahanan klaster sistem dari arsitektur dasar menjadi arsitektur berdaya tahan tinggi (High Availability & Fault Tolerance) pada seluruh tier:

A. Ketahanan Gangguan Nginx Container Mati (HA & Ingress Routing Mesh)

Tantangan: Pada arsitektur konvensional, Nginx hanya berjalan 1 replika (SPOF). Jika container Nginx mati, port 80 terputus.
Solusi Penerapan: Nginx ditingkatkan menjadi 2 Replika Aktif yang berjalan paralel di balik Docker Swarm Ingress Routing Mesh. Jika salah satu container Nginx dimatikan secara paksa, trafik port 80 dialihkan instan ke replika Nginx kedua dengan 0ms downtime, sementara Swarm secara otomatis menginisialisasi container pengganti.

# Eksekusi Uji Ketahanan Nginx: Matikan paksa 1 container Nginx $ docker rm -f $(docker ps -q -f name=wartiket_nginx | Select-Object -First 1) 3bcd6b57f3fc (Container Nginx 1 di-kill) # Hasil pengujian HTTP saat gangguan terjadi: $ (Invoke-WebRequest -Uri "http://localhost/health").StatusCode --> 200 OK (Sistem merespon instan tanpa downtime!) $ docker service ps wartiket_nginx --> Swarm otomatis memulihkan replika kedua dalam hitungan 0.8 detik (2/2 running).

B. Ketahanan Gangguan Redis Mati (AOF Volume Persistence & Auto-Reconnection)

Tantangan: Jika Redis mati mendadak, data kuota tiket dalam memori rawan terhapus dan backend Node.js berpotensi mengalami unhandled crash.
Solusi Penerapan: 1. Redis diintegrasikan dengan Docker Persistent Volume (redis-data:/data) dan mode appendonly yes sehingga mutasi kuota tiket tersimpan permanen di disk.
2. Node.js backend dilengkapi Graceful Degradation & event listener auto-reconnect (ready event). Jika Redis mati, API tidak mati melainkan merespon status terkelola HTTP 503 tanpa crash. Begitu Redis aktif kembali (1–2 detik), koneksi pulih otomatis dan sisa kuota tiket tidak hilang.

# Eksekusi Uji Ketahanan Redis: Matikan paksa container Redis $ docker rm -f $(docker ps -q -f name=wartiket_redis | Select-Object -First 1) 85d6e6928157 (Container Redis di-kill) # Respon backend Node.js saat Redis sedang mati: $ (Invoke-WebRequest -Uri "http://localhost/health").StatusCode --> 200 OK (Backend tetap hidup, redis: "RECONNECTING") # Hasil pengecekan kuota tiket setelah Redis pulih otomatis: $ (Invoke-RestMethod -Uri "http://localhost/tickets") --> stock: 980 | status: "ONLINE" (Sisa kuota tiket utuh tersimpan via AOF Volume disk!)
