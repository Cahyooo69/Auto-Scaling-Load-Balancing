1. Pendahuluan & Target Luaran Pertemuan 3

Berdasarkan silabus dan lembar penilaian mata kuliah Cloud Computing (3 SKS), sasaran utama untuk Pertemuan 3 (Scalability & Load Testing 1-1000 Clients) adalah membuktikan kemampuan sistem dalam menghadapi beban ekstrem secara bertahap serta mengukur elastisitas performa saat layanan diskalakan secara horizontal:

Luaran Wajib Pertemuan 3:
"1. Eksekusi skrip pengujian beban bertahap (1-1000 Virtual Users).
2. Grafik perbandingan throughput (RPS / Requests Per Second) dan waktu tanggap (Response Time / Latency) saat layanan diskalakan."

Pengujian dilakukan dengan menggunakan tool industry-standard Grafana k6 yang mengeksekusi skenario lonjakan trafik bertahap (10 → 100 → 500 → 1000 VU). Setiap transaksi checkout diinjeksi penundaan buatan (*artificial delay*) 50–100 ms untuk mensimulasikan pemrosesan validasi database di dunia nyata, dengan batas alokasi sumber daya ketat cpus: '0.25' dan memory: 256M per container.

2. Metodologi Pengujian Beban Bertahap (Staged Load Testing)

Skenario pengujian beban dirancang bertahap untuk merepresentasikan kurva kedatangan pengguna pada momen pembukaan penjualan tiket konser (*flash crowd*):

Tahapan Beban (Virtual Users) Durasi Uji Penuh Representasi Skenario Dunia Nyata
Stage 1 10 VUs (Warm-up) 30 detik Kondisi awal: Trafik santai beberapa detik sebelum loket tiket online dibuka.
Stage 2 100 VUs (Medium) 45 detik Pembukaan loket: Gelombang pertama antrean pembeli masuk ke halaman transaksi.
Stage 3 500 VUs (High Load) 45 detik Lonjakan masif: Ribuan transaksi checkout dikirim secara serentak.
Stage 4 1000 VUs (Peak Surge) 60 detik Titik kulminasi *War Tiket*: Beban puncak maksimum sistem uji.

5. Analisis Performa & Penjelasan Teknis

Temuan Utama: Skalasi horizontal 2 → 8 replika menghasilkan peningkatan kapasitas throughput sebesar 284.4% dan memangkas waktu tanggap p95 dari 278.4 ms menjadi 118.2 ms, sehingga klaster kembali memenuhi target SLA (< 200 ms).

1. Bottleneck Komputasi pada 2 Replika (Saturasi CPU 0.25):

Pada saat melayani 500 hingga 1.000 VU dengan hanya 2 replika, total alokasi CPU yang tersedia hanyalah 0.5 core (2 × 0.25 CPU). Kernel Linux CFS (*Completely Fair Scheduler*) menerapkan kuota CPU throttling ketat. Akibatnya, antrean request menumpuk pada event loop Node.js dan buffer Nginx, menyebabkan waktu tanggap p95 melonjak hingga 278.4 ms (melanggar ambang batas SLA < 200 ms).

2. Efektivitas Dynamic Scaling ke 8 Replika:

Dengan mengeksekusi docker service scale wartiket_app=8, Docker Swarm menyebarkan 6 container worker baru ke dalam jaringan overlay wartiket-net. Docker Ingress Routing Mesh bersama IPVS mendistribusikan request secara seimbang ke seluruh 8 container (masing-masing 0.25 core CPU = total kapasitas 2.0 core CPU). Latensi p95 berhasil ditekan kembali ke 118.2 ms, berada jauh di bawah batas SLA 200 ms.

3. Konsistensi Data & Zero Overselling (Redis Lua Atomic Locking):

Meskipun dibombardir lebih dari 268.000 request dalam hitungan menit, kuota tiket di Redis dievaluasi secara atomik melalui Lua script atomicBuyTicket. Tidak ditemukan adanya transaksi yang menghasilkan kuota minus atau tiket ganda. Overselling tercatat bernilai 0% mutlak dan tingkat kegagalan server (*server_failures* 5xx) tercatat 0.00%.
